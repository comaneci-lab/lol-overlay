# ビルドからリリースまでの手順

Windows の PowerShell で、リポジトリのルートから作業します。以下の `v0.7.1` は例です。実際のリリースでは、未使用のバージョンに読み替えてください。

## 1. ビルドの準備

1. Python、PyInstaller、Git を利用できることを確認します。実行時の依存パッケージは `python -m pip install -r requirements.txt` でインストールします。PyInstallerは別途インストールしてください。OBS連携には `obs-websocket-py`、Windows資格情報マネージャーには `pywin32-ctypes` を使用します。
2. 必要な `assets` が揃っていることを確認します。`assets` の多くは Git 管理外のため、クローンしただけでは揃いません。
3. 配布したい変更をコミットし、`main` を GitHub に push します。
4. 次のコマンドで、ビルド対象のコミットと未コミットの変更がないことを確認します。

   ```powershell
   git status --short
   git rev-parse HEAD
   ```

   リリース版ビルドは、Git 管理対象の変更や未追跡ファイルが残っていると中止されます。Git 管理外のファイルはこのチェックに含まれないため、`assets` などの内容は別途確認してください。

5. `dist` に以前のビルドの不要なファイルが残っていないことを確認します。ビルドは既存ファイルを上書きしますが、不要になったファイルをすべて削除するわけではありません。必要なファイルは退避してから整理してください。

オーバーレイの HTML・CSS・JS は LF 改行で管理します。Git とエディターの設定で LF を指定し、ビルド時にはコピー元と `dist` の両方を検査します。CRLF が残る既存ファイルはエディターで LF に変換してからビルドしてください。利用者用の `css\custom` は検査対象外です。

開発用の動作確認では `.\build.bat` のビルド種別に `1`（開発版）を選べます。開発版はタグを作成・pushせず、Releaseとのバージョン比較を行いません。`dist\.dev-environment` が更新チェックを無効にするため、開発中はそのまま使用してください。

## 2. リリース版をビルド

```powershell
.\build.bat
```

1. ビルド種別で `2`（リリース版）を入力します。
2. タグ名を入力します（例: `v0.7.1`）。形式は `v1.2.3` または `1.2.3` です。
3. ビルドの成功を確認します。現在のコミットに指定したタグがなければローカルに作成され、ビルド成功後に `origin` へ自動でpushされます。

同じコミットに同名タグがある場合は再利用されます。タグが別のコミットを指している場合は中止されます。ビルドやpushの失敗後も作成されたローカルタグは残るため、原因を解消して同じコミットで再実行できます。ビルド中にコミットや作業ツリーが変更された場合もpushを中止します。開発版ではタグをpushしません。

## 3. ビルド結果を確認

`dist\LoLAPIGet.exe` と `dist\app-update.json` が生成されていることを確認します。次のコマンドで JSON の `version` と `commit_sha` がタグと対象コミットに一致し、`sha256` が exe のハッシュと一致することも確認します。

```powershell
Get-Content .\dist\app-update.json
git rev-parse HEAD
(Get-FileHash .\dist\LoLAPIGet.exe -Algorithm SHA256).Hash.ToLowerInvariant()
```

ビルドが失敗した場合、以前の `dist` のファイルを今回の成果物として使用しないでください。

exeは単一ファイル形式で、観戦GUI用の画像を内蔵します。`_internal` フォルダーは不要ですが、HTMLオーバーレイ用の画像やHTML・CSS・JavaScriptは別途配置します。JSONは内蔵せず、実行時に必要に応じてData Dragonから取得します。

## 4. 配布 ZIP を作成

1. 新しい配布用フォルダーを用意し、`dist` の内容をコピーします。
2. リポジトリの `settings.ini`、`README.md`、`LICENSE`、`docs`、`examples/kpa` を配布用フォルダーにコピーし、配布する設定を確認します。READMEから参照するガイドと開発ガイドのサンプルを利用できるよう、ディレクトリ構成を維持してください。
3. 配布用フォルダー内の `.dev-environment` を削除します。このファイルが残ると利用者の更新チェックが無効になります。
4. `LoLAPIGet.exe`、`settings.ini`、`README.md`、`LICENSE`、`docs`、`examples/kpa`、`html`、`css`、`js`、`assets`、`config` を含む配布用フォルダーを ZIP にします。
5. ZIP に入れた exe が手順 3 の exe と同じことを確認します。ZIP 作成後に exe を変更した場合は、その ZIP と以前の `app-update.json` を組み合わせないでください。

`build\app_version.json` はビルド時に exe に組み込まれる内部ファイルです。Release に別途添付する必要はありません。

## 5. タグを確認し、GitHub Release を公開

ビルド時にタグがpushされたことを確認します。例のタグを使用した場合:

```powershell
git ls-remote --tags origin refs/tags/v0.7.1
```

1. GitHub の **Releases** で **Draft a new release** を選択します。
2. ビルド時と同じタグを選択し、リリース内容を記入します。
3. 公開前に、次の2ファイルをそれぞれ Release asset として添付します。
   - 手順 4 の配布 ZIP
   - 同じビルドの `dist\app-update.json`（名前は `app-update.json` のまま）
4. 通常の Release として公開します。

## 6. Pages の公開を確認

GitHub の **Actions** で **Publish overlay updater** が成功したことを確認します。通常の Release 公開時に、リリースタグのコミットからオーバーレイを作り、最新 Release の `app-update.json` とともに GitHub Pages に配置します。公開した Release が最新 Release でない場合や、JSON のコミットがタグと一致しない場合はデプロイを中止します。`main` への push やタグの push だけでは公開されず、プレリリース公開時もデプロイされません。

リポジトリの「Settings」→「Pages」で、公開元を「GitHub Actions」に設定してください。

`app-update.json` の添付漏れなどで失敗した場合は Release の asset を修正してから、失敗したワークフローの **Re-run jobs** → **Re-run failed jobs** を実行します。

デプロイだけが失敗した場合、アップロード済みの Pages 成果物は1日で期限切れになるため、期限切れ後は **Re-run all jobs** を選択します。ワークフローの修正前に開始された実行の再実行には、その修正は反映されません。

**Run workflow** による手動実行も可能です。この場合は最新の `main` からオーバーレイを公開するため、未リリースの変更が利用者に届くことがあります。復旧やオーバーレイ単独更新が必要な場合に利用してください。
